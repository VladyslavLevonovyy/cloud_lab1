# Лабораторна робота №1
## Хмарні технології

Виконав: Левоновий Владислав

Тема: Розгортання REST API у хмарному середовищі AWS з використанням Docker, Terraform та GitHub Actions.

## 1. Мета роботи

Навчитися запускати програми в Docker, створювати хмарну інфраструктуру за допомогою Terraform та налаштовувати автоматичне розгортання програми через GitHub Actions.

## 2. Опис проєкту

У цій лабораторній роботі я створив простий REST API для роботи з клієнтами спортивного залу.

Програму написав на Python з використанням Flask. Для зберігання інформації про клієнтів використав базу даних MySQL.

Для локального запуску програми та бази даних використав Docker і Docker Compose.

Для розгортання в AWS використав декілька сервісів. Amazon VPC потрібен для створення мережі, Amazon ECR для зберігання Docker-образів, Amazon ECS Fargate для запуску контейнера, а Amazon RDS для роботи з базою даних MySQL.

Також використав Application Load Balancer для доступу до програми через інтернет, AWS Secrets Manager для зберігання пароля бази даних та CloudWatch для перегляду журналів роботи контейнера.

Інфраструктуру створив за допомогою Terraform, а автоматичне оновлення програми налаштував через GitHub Actions.

## 3. Структура проєкту

У проєкті є основні файли app.py, Dockerfile, compose.yaml, requirements.txt та Readme.md.

У файлі app.py знаходиться код REST API на Python. Dockerfile потрібен для створення Docker-образу, а compose.yaml використовується для локального запуску програми та MySQL.

У файлі requirements.txt записані бібліотеки Python, які потрібні для роботи програми.

У папці db знаходиться SQL-файл для початкового заповнення бази даних.

У папці terraform знаходяться файли, які відповідають за створення ресурсів AWS. У них налаштовані мережа, база даних, контейнери, Load Balancer та права доступу.

У папці .github/workflows знаходиться файл deploy.yml, який використовується для автоматичного розгортання програми через GitHub Actions.

## 4. REST API

У програмі реалізовано три основні маршрути.

GET /health використовується для перевірки роботи сервера.

GET /clients повертає список клієнтів із бази даних.

POST /clients дозволяє додати нового клієнта.

Наприклад, для додавання клієнта я передавав ім'я Vladyslav та вік 19 років у форматі JSON.

Після виконання POST-запиту інформація записувалася в таблицю clients бази даних MySQL.

## 5. Локальний запуск через Docker

Для локального запуску використав Docker Desktop.

У кореневій папці проєкту створив файл .env, у якому знаходяться локальні параметри підключення до MySQL.

Для запуску контейнерів виконав команду `docker compose up --build -d`.

Після цього перевірив їхню роботу командою `docker compose ps`.

Для перевірки API використав команду `curl http://localhost:5000/health`.

Щоб отримати список клієнтів, виконав `curl http://localhost:5000/clients`.

Для додавання клієнта використав POST-запит на адресу `http://localhost:5000/clients`, у якому передав ім'я та вік клієнта.

Для зупинки контейнерів використовується команда `docker compose down`.

Для MySQL налаштував Docker Volume. Він потрібен для того, щоб дані зберігалися навіть після зупинки та повторного запуску контейнерів.

Під час перевірки переконався, що додані клієнти залишаються в базі даних після перезапуску.

## 6. Інфраструктура AWS

Для створення інфраструктури використав Terraform. Ресурси розгорнув у регіоні eu-north-1 (Stockholm).

Спочатку створив VPC з публічними та приватними підмережами. Також налаштував Internet Gateway, таблиці маршрутизації та Security Groups для контролю мережевого доступу.

Потім створив приватний реєстр Amazon ECR, у який завантажив Docker-образ програми.

Для запуску контейнера використав Amazon ECS Fargate. Базу даних MySQL розмістив у сервісі Amazon RDS.

Для доступу до програми через інтернет створив Application Load Balancer.

Також налаштував CloudWatch Logs для запису журналів роботи програми та VPC Endpoints для доступу контейнера до необхідних сервісів AWS.

Програма працює таким чином: користувач надсилає запит на Application Load Balancer, який передає його контейнеру ECS Fargate. У контейнері працює Flask API. Для отримання або збереження даних програма звертається до бази даних MySQL, яка знаходиться в Amazon RDS.

## 7. Безпека мережі

Для захисту інфраструктури налаштував Security Groups, які обмежують мережевий доступ.

Application Load Balancer приймає HTTP-запити через порт 80.

Контейнер ECS працює на порту 5000 та приймає запити тільки від Security Group Load Balancer.

База даних RDS використовує порт 3306. Доступ до неї дозволений тільки від Security Group ECS.

RDS розміщена у приватній підмережі та не має публічного доступу. Контейнер ECS також працює у приватній підмережі без публічної IP-адреси.

Для доступу контейнера до Amazon ECR та інших необхідних сервісів використав VPC Endpoints.

Пароль бази даних зберігається в AWS Secrets Manager та передається контейнеру під час запуску.

Таким чином користувач може звертатися до REST API через Load Balancer, але не може напряму підключитися до бази даних через інтернет.

## 8. Terraform

Terraform використав для автоматичного створення та керування ресурсами AWS.

Для роботи встановив Terraform та AWS CLI і налаштував підключення до AWS.

Спочатку перейшов у папку terraform за допомогою команди `cd terraform`.

Потім виконав `terraform init` для ініціалізації Terraform та `terraform validate` для перевірки правильності конфігурації.

Для перегляду запланованих змін використав команду `AWS_PROFILE=cloud-lab terraform plan`.

Для створення інфраструктури виконав `AWS_PROFILE=cloud-lab terraform apply`.

Під час першого розгортання також завантажив початковий Docker-образ у Amazon ECR із тегом, який зазначений у файлі ecs.tf.

Після створення ресурсів перевірив роботу програми через Application Load Balancer.

Для видалення інфраструктури використовується команда `AWS_PROFILE=cloud-lab terraform destroy`.

Ця команда видаляє ресурси AWS, включно з базою даних RDS, тому її потрібно запускати після завершення роботи та захисту лабораторної.

## 9. Автоматичне розгортання GitHub Actions

Для автоматичного розгортання програми налаштував GitHub Actions.

Налаштування знаходяться у файлі .github/workflows/deploy.yml.

Після кожного git push у гілку main GitHub Actions автоматично запускає процес розгортання.

Спочатку GitHub завантажує код проєкту та підключається до AWS. Потім збирає Docker-образ і присвоює йому тег на основі SHA коміту.

Після цього Docker-образ завантажується в Amazon ECR. Далі створюється нова ревізія ECS Task Definition та оновлюється ECS Service.

Для підключення до AWS використав GitHub Secrets з назвами AWS_ACCESS_KEY_ID та AWS_SECRET_ACCESS_KEY.

Також створив окремого IAM-користувача з необхідними дозволами для роботи з ECR та ECS.

Спочатку планував використати авторизацію через OIDC та підготував відповідну конфігурацію в Terraform. Але в моєму AWS-акаунті створення IAM OIDC Provider було заблоковано політикою AWS Organizations (SCP). Тому використав авторизацію через IAM-користувача та GitHub Secrets.

Під час перевірки GitHub Actions успішно виконав автоматичне розгортання програми.

Додатково я змінив маршрут /health, додавши версію програми 2.0. Після git push GitHub Actions автоматично зібрав новий Docker-образ та оновив ECS.

Після завершення розгортання нова версія програми стала доступною через Application Load Balancer.

## 10. Перевірка роботи в AWS

Після розгортання перевірив роботу програми через адресу Application Load Balancer.

Адреса застосунку:

http://levonovyi-gym-alb-745832772.eu-north-1.elb.amazonaws.com

Для перевірки стану програми відкрив адресу з маршрутом /health, а для отримання списку клієнтів використав маршрут /clients.

Також перевірив додавання нового клієнта через POST-запит.

Після налаштування GitHub Actions я змінив код маршруту /health, додавши версію програми 2.0 та повідомлення про автоматичне розгортання.

Після завантаження змін на GitHub автоматично запустився новий деплой. Коли він завершився, я відкрив /health та побачив нову версію 2.0.

Відповідь сервера містила статус ok, версію 2.0 та повідомлення Deployed automatically with GitHub Actions.

Це підтвердило, що зміни в коді автоматично потрапляють у програму, яка працює в AWS.

Адреса Load Balancer може змінитися після повторного створення інфраструктури.

## 11. Захист конфіденційних даних

Під час виконання роботи врахував основні правила захисту конфіденційних даних.

Пароль бази даних зберігається в AWS Secrets Manager, а ключі для автоматичного розгортання зберігаються в GitHub Secrets.

Файл .env не завантажується у репозиторій GitHub.

Terraform State та службові файли Terraform додані до .gitignore.

Docker-контейнер запускається від непривілейованого користувача.

Для GitHub Actions створив окремого IAM-користувача з обмеженими дозволами.

База даних MySQL доступна тільки для застосунку ECS.

Завдяки цим налаштуванням паролі та секретні ключі не зберігаються у відкритому коді проєкту.

У результаті отримав практичний досвід роботи з Docker, Terraform, AWS та GitHub Actions.
